## 2026-09-03 — расширение покрытия MCap и стабилизация котировок

- Причина пропусков MCap установлена: Blockscout не публикует `circulating_market_cap` и `exchange_rate` для значительной части новых токенов, хотя торговые пары уже существуют.
- Основным источником текущего MCap и справочной USD-цены выбран публичный API DexScreener `token-pairs/v1/robinhood/{contract}`.
- Для защиты от ложных или нерепрезентативных пулов сначала выбирается самая ликвидная пара, где котировочным активом является ETH, WETH или USDG. Только при отсутствии такой пары разрешается самая ликвидная нестандартная пара, и источник явно помечается как менее надёжный.
- Локальная контрольная проверка заполнила MCap для 24 из 25 позиций. CLIPPY определяется примерно как `$2,42M`, JINQIAN — примерно как `$0,53M`; значения меняются вместе с рынком.
- Для DISHWASHER у DexScreener не найдено индексируемой пары. В GitHub Actions добавлен резервный расчёт MCap по малой 0x-котировке и onchain `totalSupply`; если исполнимого маршрута нет, вместо выдуманного значения остаётся прочерк.
- Для полной оценки позиции основной 0x-маршрут дополнительно сравнивается со справочной spot-оценкой. При аномально слабом ответе проверяются firm quote AllowanceHolder и Permit2 price, после чего используется лучший исполнимый результат.
- Индикативный 0x-запрос синхронизирован с режимом Matcha без подключённого кошелька: `taker` не передаётся, поскольку он необязателен для `/price`. Для firm quote адрес кошелька и `sellEntireBalance=true` сохраняются, поскольку там моделируется исполнение всего фактического остатка.
- GitHub Actions теперь сохраняет последние успешные 0x-котировки в отдельном Actions Cache и восстанавливает их на следующем запуске. Срок жизни котировки в интерфейсе ограничен двумя часами; это убирает случайные прочерки при единичном сбое API, не превращая старые данные в «текущие».
- Отображение чисел унифицировано: не более двух знаков после запятой. Ненулевые ETH-значения меньше `0,01` показываются как `<0,01`, а не округляются до ложного нуля.
- В методике сайта и подвале указан DexScreener; тёмный дизайн и структура дашборда сохранены без изменений.

## 2026-09-04 — контроль свежести и более частое расписание

- Выявлено, что сайт перестал регулярно обновляться не из-за ошибки сборки: workflow оставался активным, ветка `main` была веткой по умолчанию, а все созданные запуски завершались успешно.
- Реальная причина — пропуски событий GitHub Actions `schedule`: после автоматического запуска около `09:02 МСК` новые плановые запуски несколько часов не создавались. GitHub документирует cron как best-effort механизм, который может задерживать и отбрасывать запуски при нагрузке.
- Число запланированных попыток увеличено с четырёх до двенадцати в час: cron `3-58/5 * * * *` создаёт попытку каждые пять минут со смещением от начала часа. Это снижает вероятность длинного промежутка при пропуске отдельных событий, но не превращает GitHub cron в гарантированный планировщик.
- В обзор портфеля добавлен клиентский индикатор свежести. Через 30 минут после времени снимка зелёная отметка становится янтарной и показывает текст `Данные устарели`, поэтому задержка больше не маскируется обычной подписью `Обновлено`.

## 2026-09-04 — независимый watchdog обновлений

- Повторная диагностика подтвердила систематический отказ именно GitHub `schedule`: после успешного push-снимка в `13:22 МСК` GitHub до `14:09 МСК` не создал ни одного из девяти ожидаемых пятиминутных запусков. Ошибок workflow при этом не было, потому что сами запуски отсутствовали.
- Простое дальнейшее увеличение частоты cron признано неэффективным: GitHub Actions остаётся исполнителем расчёта и публикации, но ему добавлен независимый триггер.
- В Codex создан активный локальный cron `RH Portfolio watchdog` с интервалом 15 минут. Он читает время публичного снимка и ничего не делает, пока данные моложе 20 минут.
- Если снимок старше 20 минут и рабочее дерево чистое, watchdog создаёт пустой commit `chore: refresh portfolio snapshot` и отправляет `main` в GitHub. Обычный push-триггер запускает существующий workflow с секретом `ZEROX_API_KEY`, поэтому расчёты и публикация по-прежнему выполняются только в GitHub Actions.
- Watchdog не меняет данные и исходники вручную. При грязном рабочем дереве, ошибке push или ошибке публикации он останавливается и сообщает причину; обычные успешные проверки не создают уведомлений.

## 2026-09-04 — подготовка круглосуточного облачного триггера

- Для обновлений при выключенном компьютере выбран Cloudflare Worker с Cron Trigger. Он не переносит расчёты или публикацию из GitHub: раз в 15 минут вызывает официальный GitHub API `workflow_dispatch` для существующего workflow `pages.yml` в ветке `main`.
- Расписание Cloudflare задано как `7,22,37,52 * * * *` (UTC): четыре запуска в час со смещением от наиболее загруженной нулевой минуты.
- GitHub credential не хранится в репозитории. Worker ожидает секрет `GITHUB_ACTIONS_TOKEN`; нужен fine-grained token, ограниченный репозиторием `talkhardtalk/rh-portfolio` и правом `Actions: Read and write`.
